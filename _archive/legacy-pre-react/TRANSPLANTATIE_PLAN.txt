LEESWIJZER VOOR DE AI
----------------------
Dit document is de leidraad voor een volledige transplantatie van TomeVault.
De AI mag dit document als bindende instructie beschouwen. Elke beslissing die
conflicteert met dit plan dient te worden voorgelegd aan de gebruiker voordat
er code wordt geschreven.

De gouden regel: de oude stijl, de oude layout, de oude CSS-klassen en de
oude DOM-structuur mogen op geen enkel moment worden overgenomen of "gepatcht"
in de nieuwe code. Oud gaat weg. Nieuw komt ervoor in de plaats.

DE KERN VAN HET PROBLEEM
--------------------------
De huidige app is vanilla JS die de DOM direct manipuleert.
De nieuwe app is React.
Dit zijn twee onverenigbare paradigma's. Er is geen "patch" mogelijk.
We vervangen de gehele UI-laag. De Firebase-logica overleeft — maar dan
als React hooks en callbacks, niet als DOM-manipulatie.

BESTANDSSTRUCTUUR NA TRANSPLANTATIE
--------------------------------------
WORDT VERWIJDERD of volledig overschreven:
  - index.html        → wordt minimale React shell (alleen <head> + <div id="root">)
  - style.css         → wordt teruggebracht tot alleen CSS-variabelen + font imports
  - index.mjs         → alle DOM-functies worden verwijderd
                         Firebase + data logica blijft als aparte module

NIEUWE BESTANDEN:
  - app.jsx           → nieuw React root bestand (vervangt newTomeVault.jsx)
                         Bevat alle componenten uit newTomeVault.jsx
                         + alle Firebase logica ingeplugd
  - firebase.js       → Firebase initialisatie + alle read/write helpers
                         (geëxtraheerd uit index.mjs)

OPMERKING: newTomeVault.jsx wordt hernoemd naar app.jsx.
index.mjs wordt gesplitst: Firebase-kern gaat naar firebase.js,
al het andere (DOM, screens, state object) verdwijnt.

HOE REACT EN FIREBASE SAMENWERKEN
------------------------------------
Oud patroon (vanilla JS):
  onSnapshot(handoutsRef, (snap) => {
    renderHandoutList(snap.docs);  ← manipuleert DOM direct
  });

Nieuw patroon (React):
  const [handouts, setHandouts] = useState([]);
  useEffect(() => {
    const unsub = onSnapshot(handoutsRef, (snap) => {
      setHandouts(snap.docs.map(d => ({ id: d.id, ...d.data() })));
    });
    return () => unsub();  ← cleanup bij unmount
  }, [sessionId]);
  // React herrendert automatisch als handouts verandert

Elke Firestore listener wordt een useEffect in de root TomeVaultApp of in
een custom hook. Alle setHandouts/setParty/setChat etc. vervangen de
renderHandoutList/gmPartyInlineList/chatList DOM-manipulaties.

BUILD SYSTEEM
--------------
De huidige app heeft geen build stap — index.html laadt index.mjs direct
als ES module via CDN imports. React JSX vereist een transpilatiestap.

KEUZE: Vite (aanbevolen)
  - Snel, minimale configuratie
  - Ondersteunt JSX, Tailwind, ES modules
  - Output is statische bestanden die op Firebase Hosting werken
  Commando's:
    npm create vite@latest . -- --template react
    npm install
    npm install tailwindcss @tailwindcss/vite lucide-react
    npm run build   → dist/ folder
    firebase deploy → zet dist/ live

ALTERNATIEF zonder build stap (als Vite niet gewenst is):
  - importmap + htm library (JSX-achtige syntax zonder transpilatie)
  - Dit is minder aanbevolen omdat Tailwind dan ook niet werkt
  - VRAAG GEBRUIKER VOORDAT FASE 0 BEGINT welke aanpak gewenst is

  DEEL 8: WAAROM DE JSX HET WEL DOET EN DE OUDE APP HET NIET DEED

================================================================================

Dit deel is geschreven na grondig onderzoek naar de oorzaken van het probleem.
Het is geen uitleg voor de gebruiker — het is een bindende technische instructie
voor de AI. Elke beslissing die hieronder staat moet gevolgd worden, zonder
uitzondering, voor de gehele duur van de transplantatie.


WAAROM DE JSX FILE ZO WEINIG REGELS NODIG HEEFT EN ZO GOED WERKT
-------------------------------------------------------------------

De JSX file (newTomeVault.jsx) heeft 2.352 regels en ziet er perfect uit.
De bestaande app heeft ~20.000 regels en de stijl ging nooit goed.
Dat is geen toeval. Dit zijn de structurele oorzaken:

OORZAAK 1: CSS groeit lineair, Tailwind groeit logaritmisch
  In een custom CSS codebase geldt: elke nieuwe component = nieuwe CSS regels.
  Na een jaar ontwikkeling zijn er honderden CSS klassen die elkaar overlappen,
  overschrijven en beïnvloeden via de cascade.
  
  Bewijs uit onderzoek (cssstats.com meting):
    - GitLab:    402 unieke tekstkleuren, 239 achtergrondkleuren, 59 font sizes
    - GitHub:    163 tekstkleuren, 147 achtergrondkleuren
    - Stripe:    189 tekstkleuren
  
  Dit is wat er in style.css is gebeurd. Elke keer dat een stijl "niet klopte"
  werd er een nieuwe regel aan toegevoegd, bovenop de bestaande. Het resultaat:
  een huis van kaarten waar je niets aan kunt raken zonder dat iets anders breekt.
  
  Tailwind heeft dit probleem NIET. Er zijn exact 10-12 tekst-grijstinten
  (stone-100 t/m stone-900), precies 8 amberwaarden, en die staan VAST.
  Je kunt nooit een "stone-387" uitvinden. De schaal is de schaal.

OORZAAK 2: CSS specificity oorlogen
  In de oude app staan regels als:
    .topbar .topbar__inner .brand .brand__title { font-size: 1.2rem; }
  
  En ergens anders:
    .topbar--gm .brand__title { font-size: 1.1rem; }
  
  Welke wint? Dat hangt af van specificity-berekening, volgorde in het bestand,
  en of er ergens een !important staat. Dit is de reden dat layout-aanpassingen
  "soms werken en soms niet".
  
  Tailwind heeft NUL specificity conflicten. Elke utility klasse heeft exact
  dezelfde specificiteit (één klasse-selector). De volgorde in de build output
  is deterministisch. Er zijn geen verborgen cascade-effecten.

OORZAAK 3: "Spooky action at a distance" in CSS
  Als in index.mjs staat:
    $("screenGMDash").classList.add("screen--active");
  
  Dan triggert dat CSS die in een compleet ander deel van style.css staat.
  De stijl is NIET bij de component — hij staat tientallen regels verderop,
  soms in een compleet ander blok.
  
  In React + Tailwind staat de stijl NAAST de component:
    <div className="bg-stone-900 border border-amber-900/30 rounded-xl p-4">
  Je kunt het zien, je kunt het begrijpen, je kunt het wijzigen zonder angst.

OORZAAK 4: Vaste maatschalen vs. magische getallen
  In style.css staan waarden als:
    padding: 12px 16px;
    margin-top: 14px;
    font-size: 0.875rem;
    border-radius: 8px;
  
  Dit zijn "magic numbers" — willekeurige waarden die nergens aan gekoppeld zijn.
  Elke keer dat er iets "iets groter" of "iets kleiner" moest, werd er een nieuwe
  waarde uitgevonden. Na 6 maanden zijn er 47 verschillende padding-waarden.
  
  Tailwind dwingt je te kiezen uit een vaste schaal:
    p-3 (12px), p-4 (16px), p-5 (20px), p-6 (24px)
  Je KUNT geen p-3.5 maken tenzij je het expliciet definieert.
  Dit zorgt voor visuele consistentie die onmogelijk te breken is.

OORZAAK 5: Responsive design met media queries vs. Tailwind prefixes
  In style.css:
    @media (min-width: 768px) {
      .handout-card { flex-direction: row; }
    }
    @media (min-width: 1024px) {
      .handout-card { grid-columns: 3; }  /* wacht, welk element was dit ook? */
    }
  
  Na 6 maanden development weet niemand meer welke media query geldt voor welk
  element, of ze conflicteren met andere breakpoints.
  
  In Tailwind staat alles op één regel:
    className="flex flex-col md:flex-row lg:grid lg:grid-cols-3"
  Je ziet op één plek wat er gebeurt op elke schermgrootte.
  Dit is de reden dat scaling in de JSX file perfect werkt.

OORZAAK 6: Visuele effecten vereisen exacte stacking contexts
  Effecten zoals backdrop-blur werken ALLEEN als:
    a) het element position: relative of fixed heeft
    b) er geen transform: translate3d(0,0,0) ancestor is die de stacking context breekt
    c) de juiste z-index hiërarchie aanwezig is
  
  In de oude app werden deze contexten gebroken door DOM-manipulatie
  (showOnly() togglede classes op section-elementen, wat stacking contexts
  verplaatste) en door CSS regels die overflow:hidden of transform zetten
  op container-elementen zonder dat dit bedoeld was.
  
  In React zijn stacking contexts stabiel en voorspelbaar omdat de DOM-structuur
  vast is — er worden geen elementen verborgen via class-toggling.


WAAROM GEMINI HET IN ÉÉN UUR KON BOUWEN
------------------------------------------
Dit is geen mysterie. Het heeft alles te maken met het gereedschap:

  1. Tailwind + React = visuele effecten zijn triviaal
     shadow-[0_0_15px_rgba(245,158,11,0.15)] is één woord.
     In CSS is het: box-shadow: 0 0 15px rgba(245, 158, 11, 0.15); + specificiteit check
     + zorgen dat geen parent overflow:hidden heeft
     + testen in alle browsers.

  2. Moderne AI + Tailwind werkt "vibe-first"
     Gemini (en ook deze AI) kan direct denken in visuele termen:
     "amber glow achter de kaart" → shadow-[0_0_20px_rgba(217,119,6,0.15)]
     Er is geen vertaalstap van "visuele intentie" naar "CSS implementatie"
     nodig. De Tailwind klasse IS de intentie.

  3. React componenten zijn zelfvoorzienend
     Een component in React draagt zijn eigen stijl, gedrag én structuur.
     Er is geen aparte HTML-file die je ook nog moet bijhouden.
     Dit is waarom 2.352 regels JSX meer doet dan 20.000 regels HTML+CSS+JS.

TECHNISCHE GRENZEN & RICHTLIJNEN VOOR VISUELE EFFECTEN
---------------------------------------------------------

Onderscheid: De regels hieronder zijn twee soorten.

  HARDE GRENZEN zijn browser-gedragingen die altijd breken — geen uitzondering.
  Ze zijn niet streng omdat het plan dat zegt, maar omdat de browser zo werkt.

  RICHTLIJNEN zijn aanbevelingen op basis van de bestaande JSX. Ze beschrijven
  de intentie, niet elke pixel. Er is ruimte voor afwijking als de concrete
  situatie dat vraagt — zolang het visuele resultaat klopt met de screenshot.

--- HARDE GRENZEN (browser-gedrag, altijd van toepassing) ---

GRENS V1: NOOIT overflow:hidden zetten op een container die een ambient glow
          of shimmer effect bevat. Gebruik overflow-x-hidden alleen op <body>.

GRENS V2: NOOIT transform of filter zetten op een container die backdrop-blur
          kinderen heeft. Dit breekt de stacking context en backdrop-filter werkt niet.

GRENS V3: ALTIJD position:relative op de parent van position:absolute effecten.
          Als een effect onzichtbaar is, is dit bijna altijd de oorzaak.

GRENS V4: animate-ping werkt alleen als het element display:block of display:inline-block
          is. Inline elementen negeren de animatie.

GRENS V5: group-hover effecten vereisen className="group" op de PARENT container.
          Als een hover-effect niet werkt: controleer of "group" aanwezig is op de parent.

--- RICHTLIJNEN (aanbevelingen, ruimte voor afwijking als de situatie dat vraagt) ---

RICHTLIJN V6: Shadows met rgba kleurwaarden bij voorkeur in Tailwind arbitrary syntax:
          shadow-[0_0_15px_rgba(217,119,6,0.3)]
          Liever niet in style.css, maar als een specifieke situatie dat vereist
          mag het inline via style={{}} — zolang het niet in een los CSS-bestand belandt.

RICHTLIJN V7: Glasmorfisme (backdrop-blur) testen in Safari na implementatie.
          iOS Safari heeft bekende bugs met backdrop-filter + overflow.
          Als het niet werkt: voeg -webkit-backdrop-filter toe als fallback.

RICHTLIJN V8: De perkament textuur SVG base64 string uit newTomeVault.jsx
          bij voorkeur letterlijk kopiëren. Opacity [0.03] mag licht aangepast
          worden als het visuele resultaat op het scherm beter uitkomt.

RICHTLIJN V9: Glow effecten gebruiken bij voorkeur kleuren uit het stijl-DNA
          (amber, rose, emerald). Kleine afwijkingen zijn oké als het beter
          past bij de context van het component.

RICHTLIJN V10: Responsive breakpoints bij voorkeur sm:/md:/lg: — geen custom
           breakpoints tenzij noodzakelijk. Geen losse px-waarden in media queries.


HOE TE WERKEN ALS EEN COMPONENT VISUEEL "NIET KLOPT"
------------------------------------------------------

Als een visueel effect niet zichtbaar is of anders werkt dan in de screenshot,
volg dan dit stappenplan (in volgorde):

STAP 1: Controleer overflow
  → Heeft een ancestor overflow:hidden?
  → Gebruik browser DevTools: rechtermuisknop → Inspect → kijk naar computed styles
  → Fix: verwijder overflow:hidden van de ancestor, of gebruik clip-path als alternatief

STAP 2: Controleer stacking context
  → Heeft een ancestor transform, filter, of will-change: transform?
  → Dit breekt backdrop-filter en position:fixed gedrag
  → Fix: verwijder transform van de ancestor

STAP 3: Controleer z-index hiërarchie
  → Modals: z-50
  → RightSidebar (mobiel): z-50
  → TopBar: z-30
  → Sidebar: z-30
  → Ambient glow decoraties: z-0 of geen z-index (ze zitten buiten de flow)
  → Als een element achter een ander verstopt zit: pas z-index aan volgens dit schema

STAP 4: Controleer group/group-hover
  → Staat "group" op de juiste parent?
  → Werkt de hover-trigger op het juiste element?

STAP 5: Vergelijk met de originele className in newTomeVault.jsx
  → Kopieer de exacte className string en vervang de huidige
  → Als het dan wel werkt: identificeer welke klasse weggelaten was

STAP 6: Test in Chrome EN Safari
  → Safari heeft strictere regels voor backdrop-filter
  → Als het in Chrome werkt maar niet in Safari: voeg -webkit-backdrop-filter toe


SCHAALRICHTLIJNEN — VERMIJD VASTE PIXELS WAAR MOGELIJK
---------------------------------------------------------
Dit was de directe oorzaak van de scaling-problemen uit het verleden.
Het principe: gebruik de Tailwind schaal als vertrekpunt. Als een waarde
niet in de schaal bestaat en het visueel verschil maakt, is een arbitrary
waarde of inline style toegestaan — maar het is de uitzondering, niet de norm.

LIEVER NIET (gebruik Tailwind schaal als alternatief beschikbaar is):
  ✗  style={{ fontSize: '14px' }}       → text-sm
  ✗  style={{ padding: '12px 16px' }}   → px-3 py-3
  ✗  style={{ width: '240px' }}         → w-60
  ✗  style={{ marginTop: '14px' }}      → mt-3.5

TOEGESTAAN:
  ✓  text-sm (14px via Tailwind)
  ✓  px-3 py-2.5 (via Tailwind)
  ✓  w-64 (256px via Tailwind)
  ✓  mt-3.5 (14px via Tailwind)
  ✓  Arbitrary waarden voor shadows: shadow-[0_0_10px_rgba(...)]
  ✓  Arbitrary waarden voor specifieke breedte: w-[3px] (dunne borders/indicators)

UITZONDERINGEN (en ze zijn schaars):
  - env(safe-area-inset-bottom) voor iPhone notch: dit is een CSS environment variabele,
    geen magic number. Gebruik: pb-safe (via custom utility in index.css)
  - Exacte pixel waarden voor border-stukjes: w-[1px], h-[3px] zijn acceptabel
    omdat Tailwind geen border-width 3 heeft in zijn schaal

RESPONSIVE DESIGN SCHEMA:
  Elk nieuw component volgt dit patroon:
    Mobiel eerst (geen prefix):   basis layout voor 320-639px
    sm: (640px+):                 tablet portrait aanpassingen
    md: (768px+):                 tablet landscape / kleine desktop
    lg: (1024px+):                desktop aanpassingen
  
  SPECIFIEKE LAYOUT REGELS:
    - Sidebar:    mobiel = fixed bottom bar (h-16), desktop = md:relative md:w-64
    - RightSidebar: mobiel = fixed right drawer, desktop = lg:relative lg:flex
    - TopBar:     h-14 md:h-16 (iets groter op desktop)
    - Modals:     max-w-sm voor kleine modals, max-w-2xl voor handout modal
                  Altijd: max-h-[90vh] overflow-y-auto voor lange modals
    - Tekst:      text-xs md:text-sm voor labels, text-sm md:text-base voor body


FONT IMPLEMENTATIE — WAAROM HET EERDER MISGING
-------------------------------------------------
In de oude app werden Cinzel en Open Sans geladen via een <link> in index.html.
Dan werd in style.css geschreven: font-family: 'Cinzel', serif;
Maar dit kon botsen met andere font-family declaraties hogerop in de cascade.

In de nieuwe app:
  1. Google Fonts worden geladen in src/index.css via @import
  2. font-fantasy en font-story zijn utility-klassen gedefinieerd in index.css
  3. Ze worden gebruikt via className="font-fantasy" — nooit via CSS regels
  4. Er is GEEN font-family declaratie in enig ander CSS bestand

De .font-fantasy en .font-story klassen moeten in index.css staan:
  .font-fantasy { font-family: 'Cinzel', serif; }
  .font-story   { font-family: 'Lora', serif; }

Ze worden NOOIT inline geschreven als style={{ fontFamily: 'Cinzel' }}
Ze worden NOOIT uitgeschreven als een Tailwind extend in tailwind.config
(dat is onnodige complexiteit — de utility klassen in index.css zijn voldoende)


SAMENVATTING: DE DRIE PRINCIPES DIE ALLES BEPALEN
---------------------------------------------------

PRINCIPE 1: CO-LOCATIE
  Stijl staat ALTIJD bij het component. Nooit in een aparte file.
  Als je een component aanpast, pas je de stijl in diezelfde file aan.
  Er is geen CSS file die je ook nog moet openen.

PRINCIPE 2: VASTE SCHALEN
  Elke maat, kleur, schaduw en afstand komt uit de Tailwind schaal.
  Er worden geen willekeurige waarden uitgevonden.
  Als iets "iets groter" moet, kies je de eerstvolgende schaalstap omhoog.

PRINCIPE 3: ZICHTBAARHEID
  Elk visueel effect is zichtbaar in de className string.
  Er zijn geen verborgen CSS regels die van een afstand het element beïnvloeden.
  Als het er niet in staat, doet het ook niets.

Deze drie principes zijn de reden dat de JSX file prachtige visuele effecten
heeft in 2.352 regels, en de oude app ze niet kon reproduceren in 20.000 regels.
Ze zijn ook de reden dat Gemini het in een uur kon bouwen.
Volg ze zonder uitzondering.
